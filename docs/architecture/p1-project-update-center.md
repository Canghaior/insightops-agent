# P1 项目更新中心

## 目标

把“跟踪项目”从一个个人开关扩展为可持续使用的 Release 情报入口：后台自动采集，用户在更新流中查看、筛选、标记已读，并可带着具体项目和版本进入研究问答。

## 数据流

1. 用户关注项目时把 `tracked_project.next_sync_at` 调整为当前时间。
2. Worker 每 30 秒领取到期任务；领取通过数据库锁和 `sync_locked_until` 防止重复执行。
3. Worker 只调用登记仓库的 GitHub Releases API，单次最多读取 30 条稳定版本。
4. 原始响应写入 `source_snapshot`，标准化更新写入 `intelligence_event`，二者由 `event_evidence` 关联。
5. Release 的项目和外部版本标识具备唯一约束；重复同步更新快照但不会产生重复事件。
6. 更新 API 按当前账号的工作区和个人关注状态查询，`user_event_read` 单独保存每个用户的已读状态。

## 调度与恢复

- 正常成功：默认 6 小时后再次同步。
- GitHub 限流：1 小时后重试。
- 仓库或输入无效：6 小时后重试。
- 网络或临时异常：按连续失败次数进行 5 到 60 分钟指数退避。
- 每次成功或失败都会写入 `job_task`，并更新项目的最近状态、时间、错误和失败次数。
- 单项目失败不会终止同批其他项目。

## 权限与隔离

- 所有登录用户可查看自己已关注项目的更新，并维护自己的已读状态。
- 用户不能看到其他工作区的项目或其他用户的已读状态。
- 只有 `SYSTEM_ADMIN` 可查看采集运行状态和请求立即同步；权限在服务端校验。
- 来源 URL 限定为 GitHub 官方 Release 页面，研究入口仍经过 P0 Guardrail。

## 当前边界

P1.2 只采集 GitHub Releases，不覆盖 Issue、PR、Roadmap、博客或任意仓库订阅。通知仅在站内显示，邮件、Webhook 和摘要推送留给后续版本。
