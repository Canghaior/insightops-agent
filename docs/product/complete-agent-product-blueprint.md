## 1. 文档目的

本文档用于统一回答以下问题：

1. InsightOps Agent 当前已经真正完成了什么。
2. 哪些功能只是具备页面、配置或部分代码，还没有形成完整闭环。
3. 当前知识库切片和 Embedding 完成后，接下来应该继续做什么。
4. 一个完整的 InsightOps Agent 最终应该给用户带来什么效果。
5. 项目达到什么标准后，才可以从“功能丰富的 Alpha”升级为“完整产品”。

本文档不以“代码文件是否存在”作为完成标准，而是区分四种状态：

| 状态 | 判断标准 |
|---|---|
| 已完成 | 前后端、数据持久化和关键测试均存在，并且已在目标环境形成可使用闭环 |
| 部分完成 | 已有主要代码或页面，但仍有固定数据、缺少生产验收、缺少异常处理或缺少用户闭环 |
| 未完成 | 只有规划、配置项、文档描述，或当前完全没有实现 |
| 后续扩展 | 不影响首版技术情报产品成立，可在核心产品稳定后再建设 |

## 2. 产品最终定位

InsightOps Agent 不应被定义为通用聊天机器人，也不应在当前阶段扩张成服务所有行业的万能 Agent。

完整产品的一句话定义为：

> 用户可以添加自己关注的 AI／开源项目和官方资料，系统持续采集 Release、Issue、Pull Request、Roadmap、官方文档与博客，自动识别重要变化和技术风险；用户可以基于可信证据连续提问、比较项目、生成报告，并从每个关键结论返回官方来源复核。

产品的核心价值不是“模型能够聊天”，而是：

- 持续跟踪，不依赖用户每天手工查看多个网站。
- 变化识别，过滤普通维护噪声，突出重要版本、安全修复和 Breaking Change。
- 证据可追溯，关键结论能够回到 Release、Issue、PR 或官方文档。
- 研究可复用，会话、结论、报告、长期偏好和执行记录能够沉淀。
- 过程可审计，能够查看 Agent 为什么调用工具、用了什么资料、如何形成答案。

### 5.2 当前已进入受控多轮 Agent

当前聊天研究链路已经升级为：

```text
用户问题 + 对话上下文 + 可用项目
  -> DeepSeek Planner 原生 Function Calling
  -> 同轮只读调用形成 DAG 并行层
  -> Registry 权限/Schema + 节点/Token/成本预算
  -> Executor 受限并行；写工具独占并继续审批
  -> Observation + 持久化节点状态与依赖边
  -> 根据完整层结果重规划、换工具或结束
  -> 基于累计证据流式生成答案
```

P2.0-B 已实现模型自主选择工具、Planner、Executor、Observation 和真实多轮循环；P2.0-C1/C2/C3 已补齐 Registry timeout 强制中断、客户端取消、Run 级资源预算、错误分类重试、指数退避、分组熔断、半开探测、尝试级审计与生产监控；P2.0-D 又增加了首个审批型写工具 `user_memory_upsert`、幂等 Effect、失败补偿，以及受 Workspace allowlist 约束的只读 MCP 调用。这是有边界、可观测、可恢复且对写副作用进行人工确认的受控 Agent，而不是无限自主系统。

- 多项目横向比较。
- 用户可纠正分析并形成评测样本。

### 7.8 报告与通知

- 项目日报、周报、月报和专题报告。
- 报告引用完整证据。
- Markdown、PDF 导出和分享。
- 站内、邮件和至少一种团队协作渠道通知。
- 重要风险即时通知。
- 用户自定义项目、关键词、风险和频率规则。
- 发送状态、失败重试和送达审计。

### 7.9 长期记忆

- 用户手动管理记忆。
- 自动提取偏好和稳定事实。
- 写入前让用户确认。
- 记忆来源、置信度和有效期。
- 重复合并和冲突处理。
- 用户可以查看、修改、禁用和删除每条记忆。
- Workspace 级共享知识与个人记忆分离。

### 7.10 管理与质量

- 用户、Workspace、项目和知识源管理。
- 采集、Embedding、分析、报告和通知任务管理。
- 失败任务重试和死信处理。
- 模型、Prompt、工具和配额管理。
- Run、Step、Tool Call、引用和 Trace 查询。
- RAG 评测集、历史基线和版本对比。
- 用户反馈复核。
- 发布质量门禁。

### 7.11 生产运维与安全

- CI 自动测试、构建和漏洞扫描。
- 生产审批部署、健康检查和自动回滚。
- 应用指标、日志、Trace 和告警。

- Secret 轮换。
- 磁盘、CPU、内存、队列、模型和数据库告警。
- 故障手册和发布记录。
- 公开运营阶段的 WAF、CDN、限流和安全响应流程。

## 8. 完整产品的用户最终体验

以一名 Java 架构师为例，完整产品应呈现以下效果：

```text
注册或接受团队邀请
  -> 创建技术研究 Workspace
  -> 添加 Spring AI、LangChain4j 和公司正在评估的其他项目
  -> 选择 Release、Issue、PR、官方文档和博客
  -> 系统自动完成首次采集、切片、Embedding 和质量检查
  -> 每天增量发现新版本、文档变更和重要 Issue
  -> Agent 自动分析兼容风险、迁移要求和安全影响
  -> 用户在更新中心查看重要变化
  -> 用户追问“这个版本相比上一个版本有什么变化”
  -> Agent 制定计划并调用 Release、Issue、PR 和知识库工具
  -> 返回带逐条官方引用的结论
  -> 用户纠正遗漏或确认结论
  -> 系统生成团队周报并通过邮件或企业微信发送
  -> 所有结论、引用、Run 和工具调用均可追溯
```

对用户而言，完整产品不应该要求修改代码、执行 SQL 或手工配置服务器，常用能力都应通过页面完成。

## 11. 当前不应优先扩张的范围

以下能力可以作为未来扩展，但不应在核心技术情报产品闭环前抢占优先级：

- 自动修改代码或自动升级依赖。
- 自动操作生产环境。
- 通用 Excel、CSV 和数据库分析。
- 图表 BI 平台。
- 覆盖所有行业的通用搜索。
- Kubernetes 和复杂微服务拆分。
- 多区域高可用。
- 大规模模型训练。

当前最重要的不是增加更多页面，而是让以下四条主链路达到稳定、可配置、可验证：

1. 项目与来源由用户配置。
2. 持续采集和变化识别稳定运行。
3. Agent 基于真实证据研究并返回可信引用。
4. 反馈、评测、监控、备份和恢复形成生产闭环。
