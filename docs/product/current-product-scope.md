# InsightOps 现行产品定位与范围

**InsightOps 是面向已有业务系统的升级与改造工作台。** 第一阶段服务维护 Java / Spring 系统的工程师、技术负责人和软件维护团队。他们要根据指定项目的基线和实际资料，判断一项改造会影响什么，设计可执行的验证，逐步交付可审阅的小范围改动。

本文件是产品定位、范围和功能准入的唯一现行说明，更新于 2026-11-20。以下能力以本地 IO-03A 工程提交 `58241da` 为基线。工程实现、测试和验收按日期查阅[项目进度](../../AGENT项目与进度.md)。

## 已实现到哪里

| 使用者现在可以做什么 | 结果及适用边界 |
| --- | --- |
| 建立业务系统档案，填写用途、关键流程、技术栈、问题和约束，关联可见资料 | 档案有修订。评估启动时冻结当时的输入。知识库继续采集或保存资料，关注的外部框架提供技术依据，与客户的业务系统分开管理。[系统档案实现](../../insightops-server/src/main/java/com/jundaodsj/insightops/server/businesssystem/BusinessSystemService.java) |
| 在已知当前版本和目标版本时发起升级评估，也可在目标未定时围绕具体问题发起系统决策评估 | 研究结果区分采用的输入、资料、判断与缺口。决策评估可以只选资料或不选框架和资料，缺少依据时给出待验证项。研究可按配置选用 DeepSeek 或 OpenAI 模型。[升级评估](../../insightops-server/src/main/java/com/jundaodsj/insightops/server/workflow/UpgradeAssessmentService.java) · [系统决策评估](../../insightops-server/src/main/java/com/jundaodsj/insightops/server/workflow/SystemDecisionAssessmentService.java) |
| 从历史运行保存报告，下载 Markdown / PDF，在已关联系统的决策报告和已知版本升级报告下记录验证与人工决定 | 报告保留当时的研究快照。记录者可填写未执行、受阻或已执行的验证，更正追加新版本，决定引用当时的具体版本。记录实际观察需要写明执行方法与环境。[研究报告](../../insightops-server/src/main/java/com/jundaodsj/insightops/server/report/ResearchReportService.java) · [验证记录与决定](../../insightops-server/src/main/java/com/jundaodsj/insightops/server/report/ReportReviewService.java) |
| 导入两次 Maven 构建已有的测试结果，核对差异，按验证版本交接 | 维护者提供单模块普通 Surefire XML，可附 Maven 日志、命令记录和排除方法清单。产品保存原件、计算哈希、逐项对照，并把指定验证版本、原报告和可访问的证据导出。构建和测试仍由外部执行。[工程证据与交接范围](../manual/io-05-evidence-delivery.md) |

InsightOps 自身的 PDF 字体案例做过真实模型 A/B 和局部实验。工程资料使部分建议更具体，也暴露了模型对旧配置和根因推断过强的问题。合成订单样例用于功能验收。两者均未验证外部维护团队的一项真实升级交付或购买行为。

用户负责对接，ChatGPT 负责需求、方向和交付审阅，Codex 负责开发、测试、浏览器验收和回归。Codex 在外部实际运行的命令应注明执行者、环境和结果。InsightOps 当前支持记录这些证据，客户仓库自动扫描、自动测试、自动改造均超出已实现范围。

## 下一步要验证的一次真实升级

先由实际维护者提供一项已经需要做的 Java / Spring 升级，选定可审阅的模块或关键业务流程。内部或外部团队的真实项目均可验证工程交付，案例注明其来源。具体项目、当前版本、目标版本和验收条件待对接。优先复用已有档案、资料、评估和记录功能，由维护者或经授权的协作者在项目环境执行试改或验证。

| 预期交付 | 审阅人应能核对什么 |
| --- | --- |
| 项目基线与未知项 | 提交号或可识别的构建版本、JDK 与框架版本、目标、关键链路和约束。列明已取得的构建及依赖资料，以及缺失信息会影响哪个判断。 |
| 有依据的影响清单 | 每项指出可能受影响的模块或调用，关联项目文件位置与适用版本的技术资料，分别记录已知事实、推断及待查项。 |
| 代表性试改或关键验证 | 围绕一项会改变升级决定的不确定性，交付一份可审阅的小补丁，或一项可复现的关键验证。写清范围和预期观察。 |
| 实际构建、回归或实验结果 | 保存执行者、基线、环境、命令或操作、原始输出及观察。失败也记录，受阻写明原因，未执行的验证保持待办。 |
| 后续实施与交接说明 | 把结果对应到继续、局部调整或暂缓的理由，列出影响范围、剩余风险和下一位维护者应怎样复查。 |

**后续规划**围绕这五项交付中实际暴露的缺口。例如，版本升级报告目前没有决策报告中的验证记录入口，首案可先观察维护者怎样传递验证结果、要补做多少整理，再决定是否扩展。仓库扫描器、命令执行器、自动升级模块和新增部署方案均需另立任务。

## 怎样检验市场价值

比较对象是**同一维护团队现在实际使用的工具组合**，例如 IDE、官方迁移指南、现有构建与 CI、团队已使用的改造工具。先记下原做法、已有资料、完成标准和参与人。在相同项目基线、范围与交付标准下比较。如果只能回溯上一次类似升级，标出估算部分、任务差异和复用已有成果产生的影响。

| 待验证假设 | 需要取得的证据 |
| --- | --- |
| 客户确有这项需求 | 维护者带来真实待办，说明哪些流程受影响、什么触发了升级、今天卡在哪里、原来如何解决。 |
| 客户愿意付费 | 向有预算决定权的人出示具体交付与报价，记录实际付费、有报价的试点承诺或拒绝原因。口头兴趣、承诺与付款分开记录。 |
| 总投入可以降低，交付成本可承受 | 两种做法按材料准备、查证、验证、交付四段记录各方实际工时、返工和直接费用。计入客户协作、Codex 或人工补做、模型与工具费用，同时核对交付物能否按同一条件复核。 |
| 客户会重复使用 | 首次交接后观察维护者是否把第二项独立任务带回来、哪些步骤能自行复用，以及仍需多少支持。 |

四项假设目前均待验证。记录实际观察、估算和未知项，保留投入增加、验收失败及不再使用的结果。单个案例可以暴露工程缺口，推广到其他客户还需更多独立证据。

### 现有替代方案

以下能力据各项目官方资料核对，仅作选择对照对象的依据。

- GitHub Copilot modernization for Java 涵盖应用评估、升级改动以及构建和测试。[Microsoft Learn](https://learn.microsoft.com/en-us/azure/developer/java/migration/migrate-github-copilot-app-modernization-for-java)
- AWS Transform 提供用于 Java 和 Spring Boot 升级的托管转换任务。[AWS 用户指南](https://docs.aws.amazon.com/transform/latest/userguide/transform-aws-customs.html)
- OpenRewrite 提供 Spring Boot 迁移配方，Moderne 可以跨仓库执行配方。[OpenRewrite 迁移示例](https://docs.openrewrite.org/running-recipes/popular-recipe-guides/migrate-to-spring-3) · [Moderne CLI](https://docs.moderne.io/hands-on-learning/introduction/module-1-running-recipes/)
- Konveyor / Kai 可用静态分析定位 Java 迁移问题，并辅助生成供审阅的修复。[Konveyor 文档](https://konveyor.io/docs/konveyor/kai/)

Java / Spring 是切入场景。RAG、多模型、报告和历史记录是已有工具也能提供或组合使用的手段。能否在同等交付质量下减少总投入，须由上述对照检验。

## 后续功能怎样准入

每个候选功能在进入排期前，写清四件事。

1. **谁在做哪项具体工作？** 指明维护者、升级任务和遇到困难的步骤。
2. **输入从哪里取得？** 指明项目基线、可取得的文件或运行记录、提供者和仍缺的信息。
3. **输出推进什么工程结果？** 指明它能使哪项改动得以审阅、哪次验证得以执行，或哪项决定可以交接。
4. **用哪个真实案例验证价值？** 指明案例、原有做法，以及用什么观察判断投入和交付质量的变化。

优先排真实案例已暴露的输入、验证和交付缺口。只有竞品功能名、更多模板、更多报告形式或更多 Agent 数量的提议留作备选。

早期的开源情报产品定义，以及面向运营、市场、Excel 和经营数据分析 Agent 的路线，作为历史探索保留。旧蓝图的功能清单、阶段完成率和旧试用计划只按当时范围解读。
