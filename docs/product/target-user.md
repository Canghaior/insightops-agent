# InsightOps Agent 首发用户定义

> 文档状态：首发用户已确认，待通过真实用户访谈持续验证细节
> 版本：v0.1
> 创建日期：2026-08-15
> 适用范围：行业情报 Alpha，不代表后续经营数据分析 Beta 的全部用户

## 1. 决策结论

InsightOps Agent 的首发用户锁定为：

> 需要持续跟踪 AI／开源软件项目变化的 Java 开发者、架构师和技术负责人。

首发产品优先帮助他们完成“持续跟踪项目、发现重要变化、判断技术影响、形成带来源结论”这一类工作，不做通用聊天机器人，也不同时服务所有行业和岗位。

产品对外的一句话描述暂定为：

> 持续跟踪 AI 开源项目，自动整理版本变化、重要事件和原始证据，帮助技术团队更快完成技术研究与选型。

## 2. 核心用户画像

### 2.1 主要用户

| 维度 | 描述 |
|---|---|
| 角色 | Java 开发者、架构师、技术负责人 |
| 团队规模 | 个人开发者或 3～30 人的技术团队 |
| 技术背景 | 熟悉 Java、Spring Boot、GitHub，正在使用或评估 AI 开发框架 |
| 工作目标 | 了解框架更新、评估升级影响、完成技术选型、向团队同步技术动态 |
| 信息来源 | GitHub Release、Issue、官方文档、博客、RSS |
| 当前方式 | 人工打开多个网站、搜索、阅读、复制到 Markdown 或群聊 |
| 使用频率 | 每周多次查询；每周或每月形成一次汇总 |
| 付出成本 | 信息分散、重复阅读、容易漏掉重要更新，结论缺少统一证据 |

### 2.2 次要用户

AI 产品经理和技术研究人员可以作为观察用户，但 Alpha 不为他们单独扩展工作流。只有主要用户场景稳定后，才评估是否扩大首发人群。

## 3. 用户需要完成的工作

用户真正需要完成的不是“和 AI 聊天”，而是以下工作：

1. 持续关注若干 AI 开源项目，不遗漏重要版本和变化。
2. 快速判断某次更新是否影响现有系统或技术方案。
3. 找出 Breaking Change、废弃能力、安全修复和迁移要求。
4. 比较多个框架在 Tool Calling、RAG、MCP 等能力上的变化。
5. 将零散信息整理成有原始来源的技术结论。
6. 定期生成团队可以阅读的日报、周报或专题报告。
7. 在需要复核时，能够从结论返回 GitHub Release、Issue 或官方文档。

## 4. 核心痛点

### 4.1 信息分散

同一个项目的重要信息分布在 Release、Issue、Pull Request、文档、博客和社区讨论中，用户需要在多个入口间切换。

### 4.2 更新噪声大

项目更新数量多，但真正影响技术决策的内容少。用户需要区分功能变化、修复、兼容性变化和普通维护更新。

### 4.3 难以持续跟踪

人工跟踪通常依赖记忆和临时收藏，忙碌时容易中断，也难以识别一段时间内的变化趋势。

### 4.4 结论缺少证据

传统 AI 总结可能缺少链接、引用错误或混淆不同版本。技术决策需要能够回到官方原文复核。

### 4.5 重复整理成本高

同样的收集、筛选和总结工作会在周报、技术分享、升级评审和选型报告中重复发生。

## 5. Alpha 核心场景

### 场景一：版本变化查询

用户提问：

> Spring AI 最近 30 天发布了哪些版本？有哪些重要变化？

产品必须返回版本、发布日期、重要变化摘要和可打开的 GitHub Release 来源。

### 场景二：升级影响判断

用户提问：

> Spring AI 最新版本是否包含 Breaking Change？我们升级时要注意什么？

产品必须区分官方明确说明、基于证据的推断和暂时无法确认的内容。

### 场景三：项目横向比较

用户提问：

> Spring AI 和 LangChain4j 最近在 Tool Calling 方面分别有哪些变化？

产品必须按项目组织证据，不能把不同项目或版本的内容混在一起。

### 场景四：定期报告

用户要求：

> 每周汇总我关注的 AI 框架的重要更新。

产品应生成去重、分类、带来源的周报，并保留报告所使用的证据。

## 6. 用户使用流程

```text
添加关注项目
  → 系统定时采集官方来源
  → 自动识别版本和重要事件
  → 用户查看时间线或提出问题
  → Agent 调用工具和检索证据
  → 返回带引用的答案
  → 用户打开原文复核
  → 保存或生成周报
```

## 7. Alpha 产品承诺

Alpha 必须做到：

- 跟踪不少于 10 个真实 AI／开源项目。
- 优先采集 GitHub Release，后续增加 Issue、RSS 和官方文档。
- 关键结论必须提供可打开的官方来源。
- 明确区分事实、模型总结和推断。
- 支持查看采集任务、Agent Run、工具调用和失败原因。
- 支持生成至少一种固定格式的项目周报。

Alpha 不承诺：

- 覆盖全网全部信息。
- 自动替代技术负责人做最终选型。
- 对所有编程语言和行业提供同样深度。
- 自动修改代码、升级依赖或执行生产操作。
- 提供企业级多租户和复杂审批流程。

## 8. 成功指标

### 8.1 用户价值指标

- 用户能在 5 分钟内了解一个项目最近 30 天的重要变化。
- 用户能够从每项关键结论打开对应官方来源。
- 生成一份三项目周报所需的人工整理时间明显低于手工方式。
- 试用用户愿意连续两周查看或接收项目更新。

### 8.2 产品质量指标

- GitHub Release 采集成功率达到 95% 以上。
- 已采集 Release 不重复创建事件。
- 关键事实来源覆盖率达到 100%。
- 引用链接与结论对象、项目和版本一致。
- 失败任务不存在永久停留在“处理中”的情况。

## 9. 用户验证计划

在 Alpha 大规模开发前，至少完成 3 次访谈或工作流模拟。

访谈对象优先顺序：

1. 正在使用 Spring Boot 和 AI 框架的开发者。
2. 负责框架选型、升级或技术调研的技术负责人。
3. 需要定期输出技术周报或竞品分析的产品／研究人员。

每次访谈询问：

1. 当前关注哪些开源项目？
2. 一般通过什么渠道发现更新？
3. 最近一次技术调研或升级评估是怎么完成的？
4. 哪类更新最容易遗漏？
5. 判断一次更新是否重要时会看什么证据？
6. 当前如何记录和分享调研结果？
7. 哪些内容必须人工复核？
8. 如果系统每周生成报告，什么内容会让你持续使用？

访谈完成后，应将发现记录到：

```text
docs/product/interviews/YYYY-MM-DD-用户代号.md
```

## 11. 当前决策记录

| 决策 | 结果 | 原因 |
|---|---|---|
| 首发用户 | Java 开发者、架构师、技术负责人 | 与现有技术积累最匹配，用户问题和公开数据容易验证 |
| 首发领域 | AI／开源软件行业情报 | GitHub 和官方资料可获得，适合形成带证据的公开 Demo |
| 核心价值 | 持续跟踪、变化识别、证据整理和报告 | 比通用聊天更具体，也更容易定义验收标准 |
| 首发入口 | Web 研究工作台和对话 | 同时支持主动浏览和自然语言研究 |
| 首发边界 | 只读研究，不执行生产写操作 | 降低安全风险并缩小 Alpha 范围 |

确认记录：2026-08-15，首发用户正式确定为 Java 开发者、架构师和技术负责人，Alpha 阶段先服务这三个角色。
